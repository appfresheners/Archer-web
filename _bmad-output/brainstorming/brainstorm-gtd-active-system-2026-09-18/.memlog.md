## Context (as of session start)

- Archer today = GTD _generator_: text in -> LLM -> one markdown blob out (copy/download).
- Persistence today = client-side encrypted local vault (AES-GCM in localStorage), no accounts, no server (Epic 4, NFR8).
- A saved breakdown is opaque: goal/projects/next-actions all live inside outputMarkdown as text; nothing is queryable or checkable.
- No auth, no database. Only backend is /api/generate proxying the LLM.
- Reverse Goal Setting template already defines a rich structure + status enum (Active/Paused/Not now/Someday/Completed/Archived) and a Monthly Goal Check. No Weekly Review, no contexts yet.

## Framing question

What has to be true for Archer to become a system you actually _run your life on_, not just a generator you export from?

## Decisions

- (context by user) Current system lives in Notion; leaving because Notion databases are rigid / can't be customised to how the user personally does GTD.
- (decision by user) PRIMARY MOTIVATION: a data model that adapts to the user's GTD practice AND follows GTD properly — not a generic tracker.
- (decision by user) Drop the no-account / privacy-first design. Accounts are fine. => Supabase-primary source of truth, with auth.
- (decision by user) The daily home screen = the next actions the user has COMMITTED to (GTD "Engage"), not all actions. Must be tiny, checkable, and new actions added as others complete.
- (implication) Need a distinction between "all next actions for a project" and "committed/active next actions for today/now."

### Verdict on user's Notion "is next action" checkbox approach (tested vs GTD)

- Aligned: a manual "commit/is-next-action" flag is a legit, simple driver of the Engage view. Keep it.
- Gap 1: no CONTEXT dimension — GTD sorts next actions by context so you act by what's doable now. Flat global boolean list loses "what can I do @phone in 10 min?".
- Gap 2: "stuck project" blindness — a bare boolean doesn't guarantee each active project has (at least/exactly) one next action. Need the invariant + stuck-project surfacing in Weekly Review.
- Minor: one flat global list scales poorly at 30-100 projects; needs context + area/goal roll-up.
- Recommendation: KEEP the commit flag as the daily driver, ADD (a) customizable context tag per action, (b) enforce/surface "every active project has a next action" + flag stuck ones in Weekly Review, (c) optional auto-surface next candidate action when one is checked off so the list self-replenishes.

### GTD correctness rules the build must honor

1. Capture is decision-free. 2. Clarify follows the decision tree (actionable? 2-min? delegate/defer; else trash/reference/someday). 3. Next actions = physical/visible/independent/verb-first. 4. Every active project has >=1 next action (else "stuck"). 5. Projects are not task containers (plan = support material). 6. Engage filters by context/time/energy/priority. 7. Weekly Review is first-class (Get Clear/Current/Creative). 8. Calendar = hard day/time only.

### Emerging model (GTD -> Archer tables)

inbox_items, next_actions (done flag, context, time, energy, committed/is-next flag, waiting_for state, optional date), projects (outcome; stuck flag), areas (Horizon 2, never completes), goals (Horizon 3; existing status enum Active/Paused/Not now/Someday/Completed/Archived), reviews (weekly). Contexts = user-customizable.

## User sketch (attached 2026-09-18) — the system shape

User sketched a 5-step GTD pipeline (5 columns, each with an "add" box + list):

- STEP 1 — INBOX (Capture): add box + raw items. First item shown as "Action 1 -> [proj/act]" = classify/route an inbox item to a project or convert to an action. Rest are unprocessed captures awaiting clarify. Decision-free capture then clarify.
- STEP 2 — PROJECTS (Organize): add box + projects each linked UP to a goal: P1->G1, P2->G2, P3->G2, P4->G3, P5->G4. Every project rolls up to a goal; multiple projects can share one goal.
- STEP 3 — NEXT ACTIONS (Engage): a column of CHECKBOXES only. The daily driver screen, deliberately minimal — just check off committed actions. No goal/project clutter.
- STEP 4 — GOALS (Horizon 3): add box + goals each linked UP to a LIFE AREA: G1->LA1, G2->LA2, G3->LA3, G4->LA5. Goals roll up to Life Areas. => AREAS confirmed IN, user calls them "Life Areas."
- STEP 5 — REVIEW (Reflect): review screen with prompts: what moved, blockers, learnings, processing (=clear the inbox). Reflective weekly/periodic review.

### Confirmed hierarchy (from sketch)

Life Area (LA) -> Goal (G) -> Project (P) -> Next Action (checkable, Step 3 daily screen).
Inbox item -> clarify -> becomes an Action (or a Project).
Review closes the loop (what moved / blockers / learnings / processing).

### What the sketch RESOLVES

- Areas-of-Focus layer = IN, named "Life Areas" (top of hierarchy).
- Roll-up chain is explicit and linear: LA <- G <- P <- Action.
- Step 3 daily Next Actions screen = minimal checkbox list (grouping question still open, but sketch implies flat/simple).
- Review is reflective + includes inbox processing.
- The app's primary navigation = the 5 GTD stages as 5 screens/steps.

- (decision by user) Step 3 replenishment = manual pull only. When list empties, user decides what commits next. No auto-surface.
- (decision by user) Commit flow: user reviews active projects list (Step 2), opens each project, selects/creates its next action, marks it as committed => appears on Step 3. Manual, deliberate, project-by-project.
- (decision by user) One committed next action per project at a time (strict GTD). Committing a second from the same project is blocked/nudged. Daily decision = which projects get a committed action today.
- (insight by user) Current Notion system: Kanban board (Someday/Maybe-Back, Planned, Doing, Waiting/On Hold columns). Project detail has 4 GTD planning sections: Purpose & Principles, Vision/Outcome, Ideas/Brainstorming, Organising. Task table inside each project has: Priority, Context, Energy Level, Is Next Action checkbox, Time available. Pain: 50+ projects makes filling in the 4 planning sections overwhelming.
- (insight by coach) AI-assisted Natural Planning: on project creation, AI auto-drafts the 4 sections (Purpose, Vision, Ideas, Organising) so user reacts/edits rather than faces blank page. Removes the 50+ project overwhelm.
- (decision by user) Staged AI planning — NOT all-at-once generation. Full AI dump creates long docs nobody re-reads. Principle: minimum viable planning at each stage, expand only when needed.
- (insight by coach) Allen's planning depth rule: 'as much as you need to get the project off your mind.' 80% of projects need only outcome + next action. 15% need light external brainstorm. 5% need full formal plan with all 5 phases. Mindmap (Tony Buzan method) is Allen's recommended brainstorm format — free-form, no judgment, quantity over quality.
- (decision by user) Mindmap is optional per project — explicitly opted into, not created by default. Most projects (80%) never need it. When opted in: user can seed first (optional), then AI expands/generates. Brainstorm section only appears on project detail if activated.
- (decision by user) Project status enum confirmed: Active (has committed next action), Planned (defined, not yet worked), Waiting (blocked on someone else), Someday/Maybe, Completed.
- (decision by user) Standalone next actions are first-class. No catch-all Miscellaneous project. Inbox item clarified as a single action (not multi-step) can be committed directly to Step 3 without a project. Avoids the overlooked-misc-project anti-pattern from Notion.
- (decision by user) Step 3 visually distinguishes project-linked actions from standalone actions. Both are checkable items but origin is indicated (e.g. project name tag vs no tag). List stays flat/uniform otherwise.
- (decision by user) AI generation at two levels: (1) Goal level — create a Goal, generate 3-5 projects with purpose+outcome+seed next action, land in Step 2 as Planned projects linked to that goal. (2) Project level — create project manually, hit 'Generate plan' to fill purpose+outcome+seed actions individually.
- (question by coach) When goal-level AI generation creates projects, do they land as Planned (requiring manual activation) or can any land as Active immediately? Risk: AI auto-populating Step 3 daily list without user decision.
- (decision by user) AI-generated projects land as Planned — never auto-Active. User must deliberately commit. Hierarchy rules: every Goal must link to a Life Area. Projects can link directly to a Life Area WITHOUT a goal (project->LA allowed, project->goal->LA also allowed). Filtering by Life Area and Goal required across all views (projects, goals, next actions).
- (insight by coach) Allen's Weekly Review = mechanical, not journaling. 'Tidying a workshop.' Get Clear (empty inboxes) + Get Current (every active project has next action, scan waiting-for, calendar) + Get Creative (scan Someday/Maybe + higher horizons). Reflective journaling prompts (what moved, blockers, learnings) are NOT part of GTD — they were an addition in the Notion template.
- (decision by user) Review screen = primarily mechanical and system-driven (Get Clear + Get Current + Get Creative). System pre-populates: stuck projects, unprocessed inbox count, overdue waiting-for, Someday/Maybe scan, Goals scan. Reflective prompts (what moved, blockers, learnings) kept as optional section at end.
- (decision by user) Projects hold multiple actions (the full plan/backlog). Exactly one action per project can be tagged 'is_next_action' — this is the one eligible to be committed to Step 3. Step 3 filters by: context (@computer, @phone, @errands etc — user customisable), time available, and priority. All three are Allen's Engage filters.
- (insight by coach) Allen has only one concept: 'next action' on a context list. No separate 'committed/today' layer in pure GTD. Engage = filter context list by context/time/energy/priority in the moment. The 'committed daily list' is user's personal addition from Notion practice, not GTD-native.
- (decision by user) Removed 'committed' field. Step 3 = all actions tagged is_next_action across all projects + standalone actions. No separate daily commitment layer. Engage filters (context, time, priority, energy) do the narrowing in the moment — pure GTD.
- (decision by user) Action fields finalised: text (verb-first), is_next_action (bool, max one per project), context (user-customisable tag), time_available (enum), priority (enum), energy_level (enum — Low/High focus, kept separate from context), waiting_for (nullable string), done (bool), project_id (nullable FK — null for standalone actions).
